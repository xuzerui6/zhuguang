## 一、审计结论

官网首页、登录页、学员端、教练端和运营端已经形成统一、成熟的产品视觉，无需推翻重做。公开首页能够表达北京服务、教练人工核验、首次试课、预约需教练确认和线下支付等真实规则。高权限账号可以进入学员、教练和运营三个工作区，Android 真机当前版本运行稳定，未发现原生崩溃。

当前最重要的问题已从“页面是否像一个产品”转为“系统能否安全、稳定地发布和长期运行”。现有发布阻塞主要集中在生产依赖漏洞、版本发布顺序错误、Worker 请求体完整缓存、Web 会话重复请求、Android 弱网无法自行恢复、跨端业务规则不一致，以及测试数据混入运营统计。

本轮整改必须继续遵守以下事实边界：经营地点仅限北京；运动项目可以随真实供给增加；未注册公司期间不补经营主体、备案、商户、客服或投诉资料，也不把这些缺失项列为阻塞；现有空值隐藏逻辑保持不变。

## 四、审计步骤与健康状态

### 1. 官网首页和公开定位：健康

优点：

- 首屏使用北京服务定位，没有把经营范围扩展到全国。
- 训练地点、首次试课、人工核验、教练确认和线下支付规则表达真实。
- “找教练”和“先咨询训练需求”构成清晰的主次转化路径。
- 经营主体、客服和备案空值能够隐藏，没有出现虚假占位。

需要保留的边界：

- 运动项目入口必须来自当前已发布的真实供给，不能固定展示暂无教练的项目。
- 可以继续提高产品质量，但公开文案不得使用“全国领先”作为事实宣传。

### 2. 教练目录与卡片：基本健康

优点：

- 已展示适合人群、服务区域、教学方向、试课价格和“学员指定时间、教练确认”的接单规则。
- 没有虚构评分、课程量、固定可约时间或训练照片。

问题：

- “公开资料已审核”和“未展示未经核验资料”语义重复，降低信息密度。
- “新教练”标签在部分卡片中宽度不稳定，Android 卡片还存在重复展示。
- Android 教练资质使用单行截断，可能隐藏核心核验信息。

### 3. 登录与 Web 会话：需要修复

问题：

- 有访问 Cookie 时，中间件仍调用上游 `/me`；页面布局和平台代理还会再次验证身份。
- 一次受保护页面或平台 API 请求可能形成重复身份请求，增加延迟并放大上游故障影响。
- 当前会话模型不能明确区分匿名、令牌失效和身份服务不可用。
- HTML 导航遇到身份服务故障时可能返回裸 JSON `503`，用户没有可操作的重试页面。

代码位置：

- `proxy.ts`
- `app/_lib/web-auth-refresh.ts`
- `app/_lib/web-session.ts`
- `app/_lib/web-platform.ts`
- `app/api/platform/route.ts`

### 4. 运营版本发布中心：发布阻塞

问题：

- 页面当前先创建发布清单，再上传 APK；服务端创建清单时要求 APK 已存在，因此现有顺序无法成功完成新版本创建。
- 页面允许手工填写 APK SHA，不能保证与服务端实际收到的文件一致。
- `versionCode` 使用异步数据加载前的非受控默认值，可能一直停留在 `1`。
- 版本号使用硬编码默认值，容易误复用旧版本号。
- 发布、暂停、策略变更和通知缺少统一的原因输入、确认对话框、请求幂等和完整审计事务。
- 重复点击通知可能重复群发。

代码位置：

- `app/_components/ops-pages.tsx`
- `app/api/ops/releases/route.ts`
- `server/api/releases.ts`
- `server/api/router.ts`

### 5. Worker 请求体和平台代理：发布阻塞

问题：

- JSON 读取只检查 `Content-Length` 后调用 `request.json()`，无长度头、伪造长度或分块传输仍可超限占用内存。
- 头像、售后附件和 APK 上传存在完整缓存请求体的路径。
- Web 平台代理通过 `arrayBuffer()` 和 `text()`完整缓存上行和下行内容。
- APK 上传当前上限明显高于本项目真实安装包需要，放大 Worker 内存风险。
- CORS 未完整允许附件上传所需的 `x-file-name`。

代码位置：

- `server/api/contracts.ts`
- `server/api/expansion.ts`
- `server/api/releases.ts`
- `server/api/router.ts`
- `app/api/platform/route.ts`
- `app/api/ops/releases/route.ts`

### 6. Android 弱网恢复：需要修复

问题：

- API 客户端统一使用约 4 秒超时，冷启动和 bootstrap 在移动网络下过于激进。
- 非 JSON 网关错误仍按 JSON 解析，错误类型和用户提示不稳定。
- 首次连接失败后会进入本地回退，但同步定时器只在已连接状态运行，因此不能自动恢复。
- 故障条缺少明确的“重新连接”操作。
- “审核教练缓存”会让用户误以为本地内置资料来自最近一次服务端缓存。
- Android 13 尚未明确启用预测返回回调。

代码位置：

- `app/mobile/api-client.ts`
- `app/mobile/app.tsx`
- `android/app/src/main/AndroidManifest.xml`

### 7. 项目、推荐、价格和预约规则：需要统一

- `expired`、教练拒绝和双方取消不应占用首次试课资格。

问题：

## 五、Codex 实施任务

### P0-1：升级存在安全公告的生产依赖

1. 将 `next` 和 `eslint-config-next` 升级到 `16.3.4`，同步验证 Vinext 构建。
2. 将 Tailwind/PostCSS 组合升级到兼容修复版本。
3. 锁定 `nanoid >= 3.3.18`。
4. 为腾讯云 SDK 的传递依赖使用经过测试的 `uuid >= 11.1.1` override。
5. 运行短信相关测试；若腾讯 SDK 与 override 不兼容，保留风险说明并停止发布，不得绕过测试。

验收标准：

- `npm audit --omit=dev` 不再报告高危漏洞。
- `npm run build` 和短信路径回归通过。
- 锁文件与 `package.json` 一致，无手工改写锁文件。

### P0-2：限制并流式转发请求体

1. 新建统一 `readBoundedBody`，从 `ReadableStream` 分块读取并累计实际字节数。
2. 超过限制时立即取消读取并返回 `413`，不能只相信 `Content-Length`。
3. JSON 上限设为 32 KB，头像 1 MB，售后附件 10 MB，APK 20 MB。
4. Web 平台代理直接转发 `request.body` 和 `upstream.body`，不得使用 `arrayBuffer()` 或 `text()`完整缓存。
5. 流式请求按运行时要求设置 `duplex`，保留内容类型、幂等键和必要上传头。
6. CORS 增加 `x-file-name`。

验收标准：

- 无 `Content-Length`、伪造长度和分块超限都返回 `413`。
- 超限后停止读取剩余流。
- 正常 JSON、头像、附件和 APK 上传不回归。
- 平台代理测试证明请求和响应均未完整缓存。

### P0-3：修复运营版本发布中心

1. 改为先上传 APK并取得服务端计算的可信回执，再创建发布清单。
2. 上传回执必须包含 `objectKey`、`sha256`、`sizeBytes`、`versionCode` 和 `versionName`。
3. 创建清单只接受本次上传回执，不接受客户端手工填写 SHA 或 object key。
4. 移除手填 APK SHA；包名固定为 `com.zhuguang.coachos`。
5. 版本号默认留空；发布数据加载完成后，以受控状态将 `versionCode` 设置为最高值加一。
6. 发布、暂停、策略变更和通知统一要求确认、原因和 `requestId`。
7. 写入发布业务状态、事件和审计日志时保持原子性。
8. 通知增加幂等键和数据库唯一约束，重复提交返回首次结果，不重复群发。

验收标准：

- 新版本可以按“上传 APK -> 返回可信回执 -> 创建清单”成功完成。
- SHA、大小和对象键只能来自服务端回执。
- 页面不再出现 `versionCode 1` 的异步默认值问题。
- 重复通知只产生一个通知任务和一条对应审计结果。
- 未确认、未填写原因或审计写入失败时，不改变发布状态。

### P1-1：压缩 Web 会话请求链路

1. 有访问 Cookie 时，中间件直接放行，不额外请求 `/me`。
2. 仅在访问 Cookie 缺失但刷新 Cookie 存在，或平台接口返回 `401` 时执行刷新。
3. 客户端平台请求只允许刷新并重试一次，禁止无限循环。
4. 页面布局或平台 API 在一个请求中最多验证一次身份。
5. WebSession 增加内部 `serviceStatus`，区分 `anonymous`、`authenticated`、`token_invalid` 和 `upstream_unavailable`。
6. HTML 导航遇到身份服务故障时显示带“重试”入口的页面；API 保持结构化 JSON `503`。
7. 登录页本身不得因为身份上游短时故障而被中间件阻断。

验收标准：

- 有效访问 Cookie 的普通导航不触发中间件 `/me`。
- 平台 API 令牌过期时只刷新一次并重试一次。
- 单个请求的 `/me` 调用次数不超过一次。
- 31 分钟连续会话测试通过。
- 身份上游故障时，HTML 用户看到可恢复页面，API 客户端收到结构化 `503`。

### P1-2：修复 Android 弱网恢复

1. 为 bootstrap、读取和写入使用分级超时；启动请求不少于 8 秒。
2. 响应不是 JSON 时，统一转换为 `MobileApiError`，保留状态码和可读提示。
3. 首次连接失败后按 2、5、15、30 秒退避重试。
4. 恢复成功后回到正常 15 秒同步，不继续使用退避状态。
5. 故障条增加“重新连接”，点击后立即发起一次受控重试。
6. 将“审核教练缓存”改为“本地资料可能不是最新”。
7. Android 13 启用预测返回回调，并回归现有返回键逻辑。

验收标准：

- 冷启动超时后无需重启 App 即可自动恢复。
- HTML 网关错误不会触发 JSON 解析异常。
- 手动重新连接不会并发创建多条 bootstrap 请求。
- 网络恢复后页面数据刷新，故障提示自动消失。

### P1-3：统一项目、推荐、价格和预约状态规则

1. App 首页所选项目无教练时显示该项目真实空状态，不回退展示其他项目教练。
2. 主推荐直接使用排序后的最高匹配教练。
3. 官网和 App 项目入口只展示当前已发布的北京项目。
4. Mobile Bootstrap 返回当前已发布的北京项目和区域目录，新增真实供给后自动出现。
5. 经营城市始终只有北京；不得用“北京 16 区全覆盖”等文案代替真实供给。
6. 提取共享预约状态标签、终态集合和“有效历史预约”判断。
7. `expired`、教练拒绝和双方取消不占用首次试课资格。
8. Web、App、学生时间申请和旧时段预约统一使用共享规则。

验收标准：

- 切换到无供给项目时不会出现其他项目教练。
- 推荐顺序与匹配分数一致。
- 项目入口只来自服务端已发布目录。
- 首次试课资格矩阵在 Web、App 和两套预约接口中一致。

### P1-4：隔离生产、QA 和未分类数据

1. 运营概览默认只统计 `production_eligible`。
2. 单独显示 QA 和未分类待核验数量，不把它们合并成真实业务规模。
3. 预约列表使用中文状态并增加数据分类筛选。
4. 扩展分类实体到服务线索。
5. 为匿名漏斗事件增加 `production_eligible`、`qa`、`unclassified` 分类。
6. 保留现有 14 条记录，不自动删除、不静默改成生产数据。
7. 修正“这里只汇总真实业务数据”等不符合当前统计条件的文案。

验收标准：

- 默认概览数字不包含 QA 和未分类数据。
- 分类筛选结果、总数和详情保持一致。
- 历史记录仍存在且可以追踪其分类变化。
- 新线索和匿名漏斗事件都有明确默认分类。

### P1-5：保证高权限操作与审计原子性

1. 将目录状态更新与审计日志放入同一个 D1 batch。
2. 完成确认只把唯一约束冲突映射为 `409`；其他数据库错误保留真实 `500`。
3. 检查发布、目录、实体分类和其他高权限操作。
4. 业务更新、业务事件、幂等记录和审计日志必须同成同败。
5. 对零行更新、实体不存在和状态竞争返回明确错误，不记录虚假成功审计。

验收标准：

- 人工注入审计写入失败时，业务状态不会改变。
- 并发冲突返回 `409`，数据库不可用或语法错误返回 `500`。
- 不存在的实体不会产生成功事件或审计记录。

## 六、P2 体验与代码整理

### P2-1：整理教练目录和 Android 卡片

### P2-4：拆分超长模块

- 避免在同一轮做无关样式重构或大规模目录改名。

### P2-5：清理部署资源

- 不通过删除当前仍被页面、原生包或发布下载页引用的文件来缩小体积。
